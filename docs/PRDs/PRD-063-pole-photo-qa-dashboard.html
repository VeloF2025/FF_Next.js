1. Problem Statement

Johan Scott (Field QA Lead) conducts quality assurance on pole installations by manually cross-referencing photos from four to five separate sources per pole: QField civil audit, QField optical, SharePoint (multiple people's folders), and OneDrive. Each pole requires 7 civil photos + 7 optical photos. A single PON contains dozens of poles. A full PON audit currently takes hours.

Pain points identified in meeting 2026-05-11
  • Photo hunting. No single view of all photos for one pole. Johan opens QField civil, QField optical, and SharePoint in parallel windows and cross-references manually.
  • Folder naming fragility. A single SharePoint folder name mismatch excludes all photos for that pole entirely.
  • Verification gap. Field worker says "done with pole 28" — Johan must go hunt to confirm photos actually appeared. "A lot of times he says he did it, but then he didn't."
  • Optical photos mis-filed under civil. Technicians file optical photos in QField's civil layer, creating double-check work for Johan.
  • VLM misclassification. Auto-assigned photo categories are sometimes wrong — the end plate photo also shows depth, so it should satisfy both slots.
  • No structured export. When a PON is complete, Johan has no way to produce a clean, correctly structured photo package for FiberTime submission.
  • Burnout risk. Johan: "I'm going to burn out if I can't communicate on one side and have to switch sides and do [QA] well."
Design principle from meeting

Johan works pole-by-pole within a specific PON, not across projects. The system must mirror that mental model: navigate to a PON, see all poles at a glance, click in for detail. Do not make a cross-project aggregate view the primary interface.

4. Photo Specification — QField Attributes & DB Columns

Confirm with Johan before build starts

The meeting confirmed 7 civil + 7 optical per pole. The codebase defines civil as 7 active steps (step 8 is a reserved signature slot, unused). Optical has two phases in QField: Distribution Dome (8 steps) and Main Joint (6 steps). Johan needs to confirm which of these apply per pole — does every pole have both a dome and a main joint, or only one? The exact optical slot count must be confirmed against the FiberTime spec before build.

4.1 Civil Photo Slots

QField detects civil photos by matching GPKG column names against numbered prefixes (e.g. 1. Before Markout Photo matches Step 1). FibreFlow normalises these to the DB columns below.

2 During Photo civil_step_02_during_photo ^2[\.\s].*(during|digging) Active excavation in progress, open hole with workers visible, NO pole yet

4.3 How photos arrive from QField

The pipeline from field device to dashboard has three layers:

QField app (GPKG column "3. Depth Measuring") │ ▼ scripts/extract-gpkg-photos.py │ regex match: ^3[\.\s].*(depth|measuring) │ → checklist_step = 3, step_label = "Depth Photo" ▼ qfield_photo_validations table │ photo_key = "projects/{uuid}/files/DCIM/IMG.jpg/..." │ feature_id = "A673" (pole label from GPKG) │ work_type = "pole_installation" │ checklist_step = 3 ▼ construction_qa_reviews table │ civil_step_03_depth_photo = true (boolean pass/fail only) ▼ pole_qa_photos table ← NEW for this dashboard civil_3_key = "works-qa/{project}/{pole}/civil/03_depth.jpg"

4.4 Special rule: double-duty photos

A single photo can satisfy two civil slots simultaneously — most commonly the End Plates photo (step 4) which also clearly shows the depth measurement, satisfying step 3 (Depth). The system must allow one stored photo key to be assigned to multiple slots without duplicating the file. Both slots show the same thumbnail with a badge: also satisfies: Depth.

4.5 QField write-back columns (read-only reference — do NOT use)

FibreFlow currently writes QA decisions back to QField via these GPKG columns: Q/A Civil Comments, QA Civil Comments (Mohadin variant), Status ("QA Approved" / "Rework" / "Rejected"), Q/A Date. This dashboard must NOT trigger write-back — it corrupts existing project data. The write-back feature flag is disabled and must remain so.

6.2 Pole Detail Panel

Opens as a right-side slide-in panel (not a new page) — Johan stays in context and can navigate back to the pole list without a full reload.

Panel header

  • Pole ID + status pill
  • Approve button (primary action — enabled when all 14 slots filled, or with force-approve override)
  • Download ZIP button (enabled only when approved)
  • Pole-level notes field (free text, auto-saved)

Unassigned photo tray (folder import result)

After a folder is imported, unassigned photos appear in a horizontal tray at the top of the panel. Johan drags each photo from the tray to the target slot. The tray disappears once all photos are assigned.

Photo sections

Two equal columns: Civil (left) and Optical (right). On narrow screens: civil first, optical below.

  • Filled slot: thumbnail, source badge (QField / Upload), slot name. Click → full-size lightbox.
  • Empty slot: dashed border, slot name, Upload button.
  • Double-duty indicator: small badge on the slot — "Also: Depth"
  • Slot note: optional text per slot (e.g. "blurry — retake needed")

6.3 Photo Upload

Per-slot upload

  • Click any slot → file picker (single image, jpg/png/heic accepted)
  • Drag a file directly onto a slot → assigns immediately
  • Click an occupied slot → offers replace or cancel

Folder upload (bulk import for old sites)

  • "Import Folder" button on the pole detail panel — or drag a folder onto the panel
  • System reads all image files in the folder, uploads to VF Storage under a staging path
  • Photos appear in the unassigned tray — thumbnails in a horizontal strip
  • Johan drags each from tray → target slot (civil or optical)
  • Duplicate detection by file hash — silently skips already-present images
  • VLM slot suggestion shown as a dim label on each tray item (e.g. "Likely: Depth") — Johan confirms with one click or overrides by dragging elsewhere
Old sites / SharePoint exception

For existing sites where photos are already in structured SharePoint folders (Zone / PON / Pole), the folder upload is the correct ingestion path. Johan downloads the pole folder from SharePoint, drags it into FibreFlow, assigns photos to slots. No live SharePoint sync is required in Phase 1.

6.4 QA Approval

  • Approve Pole button on the panel header
  • Standard approval: requires all 14 slots filled
  • Force approval: if slots are missing, a confirmation modal asks for a mandatory reason comment (e.g. "pole P028 physically inaccessible — 12/14 accepted by ops manager")
  • Approval records: approved_by (user ID), approved_at (timestamp), approval_note (if forced)
  • Approved poles: slots go read-only, status updates in the PON list immediately
  • Undo approval: available to super_admin and manager roles

8. Data Model

8.1 Existing tables (read from, do not modify)

TableRole in this dashboard
qfield_photo_validations Bridge table written by the GPKG extractor. Contains photo_key (VF Storage path), feature_id (pole label e.g. "A673"), work_type, checklist_step (1–8 / 11–16 / NULL), step_label. This is the source of truth for QField-originated photos.
construction_qa_reviews Stores boolean pass/fail per step (e.g. civil_step_03_depth_photo = true). No photo storage keys — this is why the new table below is needed.

8.2 New table: pole_qa_photos

Stores the actual photo storage keys per slot, approval state, and notes. Column names mirror the construction_qa_reviews boolean columns exactly, with _key suffix instead of boolean type. 

CREATE TABLE pole_qa_photos (
  id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id          UUID NOT NULL REFERENCES projects(id),
  zone_id             UUID,
  pon_id              UUID,
  pole_id             TEXT NOT NULL,   -- QField feature_id, e.g. 'A673'

  -- Civil slots — named to match construction_qa_reviews columns
  civil_step_01_key   TEXT,            -- VF Storage key for Before Photo
  civil_step_02_key   TEXT,            -- During Photo
  civil_step_03_key   TEXT,            -- Depth Photo
  civil_step_04_key   TEXT,            -- End Plates (may = civil_step_03_key, double-duty)
  civil_step_05_key   TEXT,            -- Compaction / Backfill
  civil_step_06_key   TEXT,            -- Level Check
  civil_step_07_key   TEXT,            -- After Photo
  -- civil_step_08 (Signature) intentionally omitted — unused in active workflow

  -- Optical slots — Distribution Dome (Phase A, steps 1–8)
  optical_step_01_key TEXT,            -- Dome on Pole
  optical_step_02_key TEXT,            -- Dome Label
  optical_step_03_key TEXT,            -- Open Dome
  optical_step_04_key TEXT,            -- Splice Protectors
  optical_step_05_key TEXT,            -- Slack Management
  optical_step_06_key TEXT,            -- Strength Members
  optical_step_07_key TEXT,            -- Seals & Dust Caps
  optical_step_08_key TEXT,            -- Pole ID

  -- Optical slots — Main Joint (Phase B, steps 11–16)
  -- Include only if Johan confirms pole type has a main joint
  optical_step_11_key TEXT,            -- Cable Entries
  optical_step_12_key TEXT,            -- Strength Members (joint)
  optical_step_13_key TEXT,            -- Tube Routing
  optical_step_14_key TEXT,            -- Tray Entries
  optical_step_15_key TEXT,            -- Coiling & Protectors
  optical_step_16_key TEXT,            -- Readable Labels

  -- Double-duty assignments: { "civil_step_04": "civil_step_03" }
  -- means slot 4 displays the same photo as slot 3
  double_duty         JSONB,

  -- Per-slot notes: { "civil_step_03": "blurry – retake", "optical_step_08": "unreadable" }
  slot_notes          JSONB,

  -- Source tracking per slot: { "civil_step_01": "qfield", "civil_step_03": "upload" }
  slot_sources        JSONB,

  -- Staging area for folder-imported photos not yet assigned to a slot
  staging_keys        TEXT[],          -- array of VF Storage keys awaiting assignment

  -- Approval
  approved_by         UUID REFERENCES users(id),
  approved_at         TIMESTAMPTZ,
  approval_note       TEXT,            -- populated when force-approved with missing slots

  -- Audit
  created_by          UUID REFERENCES users(id),
  created_at          TIMESTAMPTZ DEFAULT NOW(),
  updated_at          TIMESTAMPTZ DEFAULT NOW(),

  UNIQUE (project_id, pole_id)
);

CREATE INDEX ON pole_qa_photos (project_id, pon_id);
CREATE INDEX ON pole_qa_photos (approved_at) WHERE approved_at IS NOT NULL;

8.4 Initial data population from QField sync

A migration script reads qfield_photo_validations and creates / updates pole_qa_photos records for any pole already tracked: 

-- Populate civil slots from existing QField sync
UPDATE pole_qa_photos pq
SET civil_step_01_key = qpv.photo_key
FROM qfield_photo_validations qpv
WHERE qpv.feature_id  = pq.pole_id
  AND qpv.work_type   = 'pole_installation'
  AND qpv.checklist_step = 1
  AND pq.civil_step_01_key IS NULL;
-- Repeat for steps 2–7 and optical steps 1–8, 11–16

Johan opens an existing PON and sees all QField photos already in place — no re-upload required. Photos uploaded manually in this dashboard are stored in the same VF Storage bucket but under the works-qa/ prefix, distinct from the original QField paths.

10. Scope & Constraints

Hard constraint — no QField sync-back

This dashboard reads from QField (via existing sync) but must never write to QField. The QField sync-back feature overwrote pole status on existing projects and caused data corruption. The feature flag disabling it must remain active for the entire lifetime of this module.

Data safety — existing QField photos are read-only source

QField photo records in qfield_photo_validations are never modified. pole_qa_photos is a QA layer that references the same storage keys. Uploading a replacement photo creates a new storage key; the original QField photo remains untouched.

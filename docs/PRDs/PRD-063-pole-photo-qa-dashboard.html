1. Problem Statement

Johan Scott (Field QA Lead) conducts quality assurance on pole installations by manually cross-referencing photos from four to five separate sources per pole: QField civil audit, QField optical, SharePoint (multiple people's folders), and OneDrive. Each pole requires 7 civil photos + 7 optical photos. A single PON contains dozens of poles. A full PON audit currently takes hours.

Pain points identified in meeting 2026-05-11
  • Photo hunting. No single view of all photos for one pole. Johan opens QField civil, QField optical, and SharePoint in parallel windows and cross-references manually.
  • Folder naming fragility. A single SharePoint folder name mismatch excludes all photos for that pole entirely.
  • Verification gap. Field worker says "done with pole 28" — Johan must go hunt to confirm photos actually appeared. "A lot of times he says he did it, but then he didn't."
  • Optical photos mis-filed under civil. Technicians file optical photos in QField's civil layer, creating double-check work for Johan.
  • VLM misclassification. Auto-assigned photo categories are sometimes wrong — the end plate photo also shows depth, so it should satisfy both slots.
  • No structured export. When a PON is complete, Johan has no way to produce a clean, correctly structured photo package for FiberTime submission.
  • Burnout risk. Johan: "I'm going to burn out if I can't communicate on one side and have to switch sides and do [QA] well."
Design principle from meeting

Johan works pole-by-pole within a specific PON, not across projects. The system must mirror that mental model: navigate to a PON, see all poles at a glance, click in for detail. Do not make a cross-project aggregate view the primary interface.

4. Photo Specification — 14 per pole

Assumption — confirm before build

The meeting confirmed 7 civil + 7 optical per pole. The existing construction.types.ts defines civil as 7 steps exactly, and optical as two phases (Dome: 8 steps + Main Joint: 6 steps = 14 optical steps in the schema). The 7 optical slots below are assumed to be the 7 most critical dome-phase steps. Johan must confirm the exact 7 against the FiberTime spec before build starts.

Civil — 7 slots (confirmed)
1
Before Photo — undisturbed ground, chalk markings, no hole yet
2
During Photo — open excavation, workers and equipment visible
3
Depth Photo — measuring tape or ruler in hole showing depth
4
End Plates — HDPE strapping or metal hardware on pole. May share photo with slot 3.
5
Compaction / Backfill — pole standing, hole filled with sand+cement, packed surface
6
Level Check — spirit level held against the upright pole
7
After Photo — full pole standing upright, wide shot from distance
Optical — 7 slots (confirm against FiberTime spec)
1
Dome on Pole — wide shot of splice dome installed on pole
2
Dome Label — dome label with Pole ID / Fibre ID clearly readable
3
Open Dome — fibre routing and tray layout visible inside open dome
4
Splice Protectors — splice protectors fitted correctly over fibre splices
5
Slack Management — neat fibre loops and organized cable within dome
6
Seals & Dust Caps — dome sealed, dust caps on unused ports, cable ties white (not black)
7
Pole ID / SJC Label — Pole ID tag attached to pole near dome, clearly readable

Special rule: double-duty photos

A single photo can satisfy two slots simultaneously — e.g. the end plate photo often shows both hardware and hole depth. The system must allow one stored photo to be assigned to multiple slots without duplicating the upload. When a double-duty assignment exists, both slots show the same thumbnail with a small badge: also satisfies: Depth.

6.2 Pole Detail Panel

Opens as a right-side slide-in panel (not a new page) — Johan stays in context and can navigate back to the pole list without a full reload.

Panel header

  • Pole ID + status pill
  • Approve button (primary action — enabled when all 14 slots filled, or with force-approve override)
  • Download ZIP button (enabled only when approved)
  • Pole-level notes field (free text, auto-saved)

Unassigned photo tray (folder import result)

After a folder is imported, unassigned photos appear in a horizontal tray at the top of the panel. Johan drags each photo from the tray to the target slot. The tray disappears once all photos are assigned.

Photo sections

Two equal columns: Civil (left) and Optical (right). On narrow screens: civil first, optical below.

  • Filled slot: thumbnail, source badge (QField / Upload), slot name. Click → full-size lightbox.
  • Empty slot: dashed border, slot name, Upload button.
  • Double-duty indicator: small badge on the slot — "Also: Depth"
  • Slot note: optional text per slot (e.g. "blurry — retake needed")

6.3 Photo Upload

Per-slot upload

  • Click any slot → file picker (single image, jpg/png/heic accepted)
  • Drag a file directly onto a slot → assigns immediately
  • Click an occupied slot → offers replace or cancel

Folder upload (bulk import for old sites)

  • "Import Folder" button on the pole detail panel — or drag a folder onto the panel
  • System reads all image files in the folder, uploads to VF Storage under a staging path
  • Photos appear in the unassigned tray — thumbnails in a horizontal strip
  • Johan drags each from tray → target slot (civil or optical)
  • Duplicate detection by file hash — silently skips already-present images
  • VLM slot suggestion shown as a dim label on each tray item (e.g. "Likely: Depth") — Johan confirms with one click or overrides by dragging elsewhere
Old sites / SharePoint exception

For existing sites where photos are already in structured SharePoint folders (Zone / PON / Pole), the folder upload is the correct ingestion path. Johan downloads the pole folder from SharePoint, drags it into FibreFlow, assigns photos to slots. No live SharePoint sync is required in Phase 1.

6.4 QA Approval

  • Approve Pole button on the panel header
  • Standard approval: requires all 14 slots filled
  • Force approval: if slots are missing, a confirmation modal asks for a mandatory reason comment (e.g. "pole P028 physically inaccessible — 12/14 accepted by ops manager")
  • Approval records: approved_by (user ID), approved_at (timestamp), approval_note (if forced)
  • Approved poles: slots go read-only, status updates in the PON list immediately
  • Undo approval: available to super_admin and manager roles

8. Data Model

The existing construction_qa_reviews table stores boolean pass/fail flags only — no photo storage references. A new table is required: 

CREATE TABLE pole_qa_photos (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id        UUID NOT NULL REFERENCES projects(id),
  zone_id           UUID,
  pon_id            UUID,
  pole_id           TEXT NOT NULL,          -- e.g. 'A673'

  -- Civil slots (7)
  civil_1_key       TEXT,                   -- VF Storage key
  civil_2_key       TEXT,
  civil_3_key       TEXT,
  civil_4_key       TEXT,                   -- may equal civil_3_key (double-duty)
  civil_5_key       TEXT,
  civil_6_key       TEXT,
  civil_7_key       TEXT,

  -- Optical slots (7)
  optical_1_key     TEXT,
  optical_2_key     TEXT,
  optical_3_key     TEXT,
  optical_4_key     TEXT,
  optical_5_key     TEXT,
  optical_6_key     TEXT,
  optical_7_key     TEXT,

  -- Per-slot notes: { "civil_4": "blurry – retake", "optical_7": "pole tag unreadable" }
  slot_notes        JSONB,

  -- Source tracking
  qfield_sync_ref   TEXT,                   -- QField record ID if photo came from sync

  -- Approval
  approved_by       UUID REFERENCES users(id),
  approved_at       TIMESTAMPTZ,
  approval_note     TEXT,                   -- populated on force-approve

  -- Audit
  created_by        UUID REFERENCES users(id),
  created_at        TIMESTAMPTZ DEFAULT NOW(),
  updated_at        TIMESTAMPTZ DEFAULT NOW(),

  UNIQUE (project_id, pole_id)
);

CREATE INDEX ON pole_qa_photos (project_id, pon_id);
CREATE INDEX ON pole_qa_photos (approved_at) WHERE approved_at IS NOT NULL;

Storage paths

works-qa/{project_id}/{pole_id}/civil/{slot}-{slug}.jpg
works-qa/{project_id}/{pole_id}/optical/{slot}-{slug}.jpg
works-qa/{project_id}/{pole_id}/staging/{uuid}.jpg     ← unassigned tray items

QField photo migration

Existing QField sync already stores photos in VF Storage via qfield_photo_validations. A one-time migration script populates pole_qa_photos from those records for any pole already tracked — Johan sees existing photos on first open, no re-upload needed.

10. Scope & Constraints

Hard constraint — no QField sync-back

This dashboard reads from QField (via existing sync) but must never write to QField. The QField sync-back feature overwrote pole status on existing projects and caused data corruption. The feature flag disabling it must remain active for the entire lifetime of this module.

Data safety — existing QField photos are read-only source

QField photo records in qfield_photo_validations are never modified. pole_qa_photos is a QA layer that references the same storage keys. Uploading a replacement photo creates a new storage key; the original QField photo remains untouched.

## Context the next session needs

**Why these design choices (so nobody re-litigates):**

- **`master_tracker` is a real table, not a view.** The spec originally proposed `vw_master_tracker` view but the live DB audit found `master_tracker` already exists with 73 columns matching the Excel exactly. Use the table directly. Service-layer broadcast keeps it in sync with `drops`/`sow_poles`/`pon_stage_tracking`/`oes_activations` writes.
- **`pon_tracker_entries` was never deployed.** The migration file in the repo is dead code. The actual table is `pon_tracker` with 1 test row. Treat as dormant; retire in 1.0c.
- **`pon_no` is zone-level (= Excel `Z PON`). `hld_pon` is project-level.** Different identifier scopes — easy to confuse.
- **`master_tracker.project_id` and `pon_tracker.project_id` are `text`** (uuid stored as string). All other tables use `uuid`. Cast at boundaries.
- **`pon_change_log` FKs are `ON DELETE SET NULL`** (not CASCADE) and `chk_pon_or_drop` was dropped. Audit rows survive parent deletion. Application enforces "every audit row references at least one entity at INSERT time" — DO NOT re-add `chk_pon_or_drop`.
- **`pon_manual_overrides` is lazy-insert (1:1 with `pon_stage_tracking`).** Every join must use `LEFT JOIN` — INNER JOIN silently drops PONs that have never been edited.

**Free wins already on prod (don't rebuild):**
- `v_pole_completion` (per-pole, with civil/optical/stringing discipline breakouts)
- `v_pon_pole_progress` (1,713 rows aggregating to PON level — for the 1.0c home dashboard)
- `pon_boundaries` (1,617 PON polygon geometries — for the 1.2 map lens)
